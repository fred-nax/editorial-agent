## 1. Cause exacte de l’incohérence

**Cause établie :** l’interface `/usage` et la ventilation article affichent une **lecture unifiée** qui mélange :

1. les événements du registre `OpenAiUsageEvent` (nouveaux) ;
2. les coûts LLM historiques `ArticleGeneration.estimatedCost` (legacy).

Pendant la recette V7.15.0 déclarée, les montants visibles pouvaient donc provenir **uniquement du legacy** — sans aucune ligne dans `OpenAiUsageEvent`.

Le contrôle pré-commit (15 générations, 0 `OpenAiUsageEvent`) était **cohérent avec PostgreSQL**. La contradiction venait d’une **interprétation UI** : des coûts historiques présentés comme des « nouvelles consommations » enregistrées.

**Preuve :**

| Base | `ArticleGeneration` | `ArticleFeaturedImage` | `OpenAiUsageEvent` | Dernière génération |
|------|---------------------|------------------------|--------------------|---------------------|
| `naxialis_agent` | **15** | **9** | **0** | 2026-11-25T16:41:16Z — Webflow « AI agents » (`cmwwetzet000b5waxg3obu8vi`) |
| `naxialis_agent_v7113_migtest` | 13 | 7 | 0 | 2026-11-24T19:12:54Z (copie / fixture) |
| `naxialis_agent_v7111_migtest` | 13 | 7 | table absente (−1) | idem ancien snapshot |

Aucune `ArticleGeneration` WordPress postérieure au 2026-11-16 n’existe en local. **La génération de recette V7.15.0 n’a pas été retrouvée** dans `naxialis_agent` ni dans les bases migtest.

## 5. Provenance des coûts affichés dans l’interface

| Surface | Source réelle |
|---------|---------------|
| `/usage` total connu | `OpenAiUsageEvent` **+** legacy `ArticleGeneration.estimatedCost` (si pas déjà couvert par un event `article_generation`) |
| Carte « Registre » | compteur **uniquement** `OpenAiUsageEvent` + coût registre |
| Bandeau amber legacy | explicite si `legacyLlmCount > 0` |
| Bandeau « registre vide » | si `registryEventCount === 0` |
| Dashboard | ventilation registre vs LLM historiques |
| Détail article | préfère events ; legacy seulement si aucun event LLM ; bandeau si `usageTracking.failures` dans `trace` |
| Export CSV | mêmes lignes unifiées (flag legacy) |

Pendant la recette V7.15.0, avec **0** event registre, tout montant affiché provenait du **legacy** (ou de calculs dérivés), **pas** d’un nouvel `OpenAiUsageEvent`.

## 6. Correctifs appliqués

1. **Garde bases** (`lib/db.ts`)  
   - `databaseNameFromUrl` / `isMigtestDatabaseUrl` / `assertApplicationDatabaseAllowed`  
   - refus de migtest pour le serveur applicatif sauf `ALLOW_MIGTEST_DATABASE=1` ou process de test automatisé  
   - détection test robuste sous `tsx --test` (`--test-*` dans `execArgv` + fichiers `*.test.ts`)  
   - log de connexion : nom de base + flag migtest (sans secrets)  
   - `PRISMA_CLIENT_TOKEN` → `openai-usage-events-v7151-20261125`

2. **Tracker** (`lib/openai-usage-tracker.ts`)  
   - contrôle délégué Prisma `openAiUsageEvent`  
   - journalisation d’échec enrichie (opération, génération, image)  
   - jamais de relance OpenAI ; jamais d’échec métier

3. **Marqueur consommation incomplète** (`lib/openai-usage-tracking-status.ts`)  
   - fusion non destructive dans `ArticleGeneration.trace.usageTracking.failures`  
   - branché sur génération article (`lib/generation.ts`) et images (`lib/images/service.ts`)  
   - UI article : bandeau « suivi incomplet » (pas un coût zéro)

4. **Provenance UI**  
   - `UsagePageClient`, dashboard, agrégats (`registryEventCount`, `registryKnownCostUsd`, `coverageNote` clarifiée)

5. **Tests**  
   - `tests/openai-usage-v7151.test.ts` (garde + marqueur)  
   - `tests/openai-usage-prisma-v7151.test.ts` (persistance réelle migtest)  
   - ajustement token Prisma dans `tests/opportunities-load-v75.test.ts`

**Hors scope volontaire :** pas de migration Prisma supplémentaire ; pas de modification des agents OpenAI ; pas de backfill ; pas de transfert inter-bases.
